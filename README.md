# BITwiki V2

**BITwiki V2 is the source-controlled knowledge architecture and public corpus for BITwiki.**

This repository contains the deployable MediaWiki content, semantic model, composition layer, runtime-facing configuration, migration evidence, and validation tooling used to develop V2 from the preserved V1 system.

- **BITwiki:** https://bitwiki.org/
- **BIThub:** https://hub.bitwiki.org/
- **Canonical branch:** `main`
- **Repository status:** V2 architecture/substrate under active development; V1 preserved as provenance evidence

> `main` is the integrated source of truth. Working branches are temporary implementation surfaces and should be merged or retired once their work is resolved.

---

## What this repository owns

BITwiki is not just a directory of articles. V2 treats the wiki as a composable knowledge system built from native MediaWiki primitives.

```text
knowledge       → pages / knowledge objects
composition     → templates / transclusion / Lua
semantics       → SMW properties / concepts / queries
operations      → Cargo workflows where repeated records justify tables
navigation      → categories / portal titles / indexes / semantic views
provenance      → preserved V1 archive + migration evidence
validation      → structural, semantic, workflow and substrate audits
```

The repository is the review and transport surface for those layers. **Filesystem folders are mappings to wiki/runtime surfaces; they are not themselves the ontology.**

## V1 → V2

V2 does not treat V1 as disposable scaffolding.

```text
V1
→ preserve
→ understand
→ identify signal
→ mature primitive
→ enhance
→ integrate into V2
```

V1 supplied much of the architectural imagination: ontology, epistemics, modular composition, semantic relationships, portals, confidence systems, transclusion, schema, and graph-oriented navigation. V2 is the attempt to give those ideas a coherent, executable substrate without flattening what made V1 distinctive.

`archive-v1/` is therefore **evidence and lineage**, not deployable V2 content and not an alternate canonical branch.

## Knowledge architecture

A BITwiki knowledge object is not defined by its folder alone.

```text
                         KNOWLEDGE OBJECT
                               │
       ┌───────────────────────┼────────────────────────┐
       │                       │                        │
    IDENTITY                CONTENT                 EPISTEMICS
       │                       │                        │
 Entity type               Book Matter              Evidence
 Domain(s)                 Overview                 Sources
 Relationships             Theory / model           Provenance
 Scope                     Mechanism                Standing
                            Methods                  Uncertainty
                            Applications             Review
                            References               Lifecycle
       │                       │                        │
       └───────────────────────┼────────────────────────┘
                               │
                         NAVIGATION / VIEWS
          Category · Portal-title · Outline · Index · Query · Graph
```

The major separations are deliberate:

```text
filesystem path
≠ MediaWiki namespace unless mapped
≠ entity type
≠ knowledge Domain
≠ Book Matter
≠ epistemic standing
≠ lifecycle
≠ semantic relationship
≠ navigation view
```

## Native substrate

Use the native MediaWiki layer that matches the job.

| Need | Primitive |
|---|---|
| canonical independent knowledge | page / knowledge object |
| repeated rendering + metadata | Template |
| reusable non-trivial logic | Scribunto `Module:` |
| graph assertion | SMW `Property:` |
| reusable computed semantic set | SMW `Concept:` |
| qualified or nested semantic fact | SMW subobject when justified |
| repeated operational records | Cargo |
| browse hierarchy | Category |
| authored reuse | transclusion |
| exploration | `#ask`, Browse, Network, facets/drilldown |

`Template:Knowledge object` provides explicit identity semantics and invokes `Module:Structure` as a validation backstop.

Cargo is intentionally bounded. `Template:Knowledge request` stores request records in `Knowledge_requests`; `BITwiki:Requested knowledge` queries them. Cargo does **not** replace SMW as the canonical semantic graph.

## Request → canonical lifecycle

Missing coverage is represented as an operational request rather than a pseudo-article.

```text
requested → researching → drafting → review → satisfied
                                      ↘ declined
```

The key invariant is:

```text
active request
≠ canonical Main page
```

When a requested subject becomes canonical, its request becomes `satisfied` and links to the canonical page. The approved initial Computer science wave currently demonstrates that lifecycle with:

- Computation
- Data structure
- Program (computing)
- Programming language
- Software

## Validation

Run the architecture checks locally with:

```bash
python scripts/validate_v2.py
python scripts/audit_substrate.py
python scripts/audit_workflow.py
python scripts/audit_mainspace.py
python scripts/inventory_corpus.py
python scripts/classify_v1_page_roles.py
python scripts/classify_v1_architecture_families.py
```

These checks cover deployable structure, references, controlled vocabularies, Domain coverage, SMW/Lua/Cargo usage, request lifecycle consistency, Main-namespace roles, and V1 migration evidence.

Generated audit JSON is **run evidence**, not canonical source. CI uploads it as GitHub Actions artifacts and does not commit it back into `main`.

---

## Deployment

Repository validity does not by itself prove deployed MediaWiki runtime state.

In particular, Cargo tables must be created or recreated in the target MediaWiki installation after the declaring template is deployed. For the current request workflow, deployment must establish `Knowledge_requests` and then verify the table/query surfaces in MediaWiki.

See [`BITwiki/Deployment prerequisites.mediawiki`](BITwiki/Deployment%20prerequisites.mediawiki) for the deployment order and runtime checks.

---

## Branch policy

**`main` is the only canonical integrated state.**

Branches may exist temporarily for reviewable work, but architecture, corpus, or migration state should not remain indefinitely stranded on side branches. Once work is accepted it belongs in `main`; obsolete or superseded branches should be retired.

A branch name is not a second BITwiki version.

## Contributing

Before adding or changing content:

1. determine whether the change is canonical knowledge, architecture, navigation, operational state, or provenance;
2. use the native MediaWiki/SMW/Cargo primitive appropriate to that role;
3. preserve V1 lineage where it materially informs V2;
4. do not manufacture semantic certainty through defaults;
5. keep requests distinct from canonical pages;
6. run the validation/audit suite;
7. integrate accepted work into `main`.

See [`BITwiki/Contributing.mediawiki`](BITwiki/Contributing.mediawiki) for the operational contribution workflow.
